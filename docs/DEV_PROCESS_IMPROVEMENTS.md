# 開發流程改善：為什麼會「來回修正」，怎麼系統性避免

- 日期：2026-06-06
- 緣起：全市場三訊號全部消失一案，從「以為資料平淡」一路追到「兩層快取 + 衍生快取 stale + 移除機能連帶刪功能 + 結構性死訊號」。
- 對應：[SIGNAL_NO_HIT_AUDIT.md](SIGNAL_NO_HIT_AUDIT.md)、[SIGNAL_NO_HIT_RETRO.md](SIGNAL_NO_HIT_RETRO.md)

## 一、來回修正的真正共通點

這次不是「一個 bug 修很多次」，而是**系統不會自己喊痛**——壞掉的東西長得跟正常一樣，要等人肉眼發現「怎麼沒訊號」才開始查。具體共通點：

1. **衍生結果壞掉時無聲無息**：快照全 0 跟「市場平靜」外觀相同，沒有任何 assertion / 告警。
2. **資料新鮮度不可見**：data/cache 停在 5/22、cloud-cache 到 6/05，畫面上看不出來，使用者無從判斷自己看的是不是舊資料。
3. **移除機能沒有盤點下游**：砍 flow 連帶讓吃貨默默下線，commit message 沒記。
4. **「永遠 False」沒被當異常**：停損在全市場恆 0、吃貨被刪後恆 0，都跟「剛好沒觸發」無法區分。
5. **測試沒有 gating**：6 個既有測試早就紅著（backtest 日期 off-by-one、favorites tags、mock spec），但沒擋住任何 commit，等於沒在守。

一句話：**缺少「讓系統自己回報健康狀態」的機制**，所有異常都靠人發現，自然會來回。

## 二、已經做掉的（本次）

- **衍生快取 sanity guard**（#3）：完整全市場掃描但 has_exit 全 0、且既有快照原本有訊號 → 判定 degraded，拒絕覆寫好快照、壞結果存 `_rejected_` 留證。
- **掃描序列化 lock**（#3）：同程序內不允許兩個全市場掃描交錯寫同一份 parquet。
- **訊號語意分層**（#2）：停損等持倉專屬訊號用 `holdings_context` 旗標，全市場不再算、前端不再顯示死欄。
- **吃貨改用真實個股資料**（#1）：不再依賴「全市場數字蓋到每檔」的假 flow。

## 三、建議再做（依投報率排序，尚未實作）

### P0 — 每日不變式健康檢查（最高投報，直接終結這類「沒人發現」）
一支排程腳本，對最新快照斷言「應恆成立」的不變式，違反就告警（Email/LINE，通道已有）：
- 完整全市場掃描 `rows >= 3000` 時，`has_exit` 數量必須落在合理區間（例如 1~800），**不可為 0**。
- 任何訊號旗標**不可全市場同值**（全 True 或全 False）→ 抓「結構性死訊號 / 假訊號」。
- `latest_price` 非空覆蓋率 > 95%。
- 資料新鮮度：cache 內最新交易日距今 < N 個營業日。

→ 這一條若早就在，stale 快照當天就會被喊出來，不會等到人肉發現。

### P1 — 資料新鮮度可見化
- 前端全市場頁顯示「資料截止日 + 來源層」。
- `/data/overview` 增加 `cache vs cloud-cache 最新交易日差異`，差異 > 0 就黃燈，提示「該按同步」。
→ 根治「使用者不知道自己看的是舊資料」。

### P1 — 單一原子同步動作鏈
- 把 cloud-fetch → 複製 cloud-cache→cache → 重算快照，收斂成**唯一**入口（`/cloud-sync` 已是雛形），移除會讓兩層 diverge 的其他手動路徑。
- 抓取（寫 cloud-cache）與掃描（讀 cache）跨程序加檔案鎖，避免邊抓邊掃讀到半截檔。

### P2 — 移除機能的依賴盤點 checklist
移除任何資料/欄位/endpoint 前，PR 描述必須附：
- `grep` 出的下游消費者清單
- 每個下游的處置（一起下線 / 換資料源），以及「下線了什麼功能」明確寫進 commit message。

### P2 — 測試 gating（CI / pre-commit）
- 現在 6 個測試長期紅著卻沒擋 commit。設 pre-push 或 CI 跑 `pytest`，紅的先修或標記 xfail，讓「綠燈」重新有意義。
- 加一份**黃金測資**（已知預期訊號數的小 universe），每次改動跑，數量大幅偏離就擋。

## 四、落地順序建議

1. 先做 **P0 不變式健康檢查**（小、獨立、直接堵住這次的洞）。
2. 再做 **P1 資料新鮮度可見化 + 單一同步鏈**（根治多 source of truth）。
3. **P2 checklist + CI** 屬流程習慣，隨時可立。

> 核心原則：不要再靠「人肉發現異常」。讓系統在資料 stale、訊號結構性死掉、衍生快取壞掉時**自己回報**，才不會每次都來回追。
