# 開發判斷與不確定記錄

## 2026-06-07 三盤濾網選股（每日 10 分鐘三盤）

### 心法 → 日本市場對映決策
| 心法盤次 | 台股原意 | 日本對映（本次實作） | 真實個股資料源 |
|---------|---------|---------------------|---------------|
| 第一盤 連續性 | 同一券商分點連續 3 天買超 | 同一 EDINET 申報人（5% rule）在窗口內重複申報（350/360）≥ N 次 | `data/cache/edinet/daily/*.json` |
| 第二盤 成本 | 分點近 5 日買超均價，現價 ≤ +5% | 主力成本＝各申報日鄰近收盤均價，現價 ≤ +5% | `data/cache/{code}_price.csv` |
| 第三盤 戶數 | 集保戶數連續減少 | 信用残（融資 margin_long）連續 N 週下降 | `data/cache/{code}_margin.csv` |

### 阻塞決策（選最合理選項繼續）
1. **「連續 3 天」→ 「窗口內 ≥2 次申報」**：EDINET 大量保有/変更報告書非每日申報（事件驅動，相隔數日～數週），
   無法逐日連續。改以「同一申報人在 60 日窗口內重複申報次數」近似「同一主力連續建倉」，門檻預設 2 次
   （`POCKET_GATE1_MIN_FILINGS`）。要更嚴可調高。
2. **主力成本無申報價欄位**：EDINET metadata 不含申報人取得均價。改以「申報日當天鄰近收盤」當該批成本，
   多次申報取均值＝主力成本帶。屬近似，非主力真實成本。
3. **第二盤「現價 ≤ 成本 +5%」包含「現價遠低於成本」**：如 6173 主力成本 119、現價 16（溢價 -86.6%）仍過關。
   邏輯上「未追高」即可，故保留；但 -80% 這種多半是反向分割/資料對齊問題，列為下方待查。

### 不確定 / 待查
- **6173 等極端負溢價**：price CSV 與 EDINET 申報日的價格量級對不上（疑似股票分割未還原或資料源錯位）。
  目前不影響濾網邏輯正確性（仍是真實個股資料、各檔不同），但「主力成本」數值需後續用還原股價校正。
- **EDINET daily 快取僅 2026-04-04～05-03（30 日）**：候選池 638 檔受此窗口限制。
  正式上線需排程每日回補 `edinet/daily/*.json`（cloud_fetch 已能抓，但目前寫 watchlist 範圍的 cloud-cache，
  全市場 daily 快取的回補管線待接）。
- 第二盤的「鄰近收盤」取「不晚於申報日的最後一筆」；若 price CSV 起始日晚於申報日則退而取最早一筆，可能高估/低估成本。

### 不變式（未破壞既有管線）
- 完全新增模組（`pocket_filter.py` / `pocket_service.py` / `routers/pocket.py` / `/pocket` 前端），
  未改 signals 掃描、analyzer、快照 parquet 管線；既有測試不動。
- 三盤輸入皆為「單一個股」真實資料，未使用已知失效的「全市場數字攤平到每檔」flow。
  證據：7922 與 4452 的申報人、申報次數、margin 序列、現價皆不同（見對話走查）。
