# 回顧調查報告：全市場三訊號全部消失，為什麼會發生？

- 日期：2026-06-06
- 對應審計：[SIGNAL_NO_HIT_AUDIT.md](SIGNAL_NO_HIT_AUDIT.md)
- 問題現象：抓了最新資料後，全市場畫面看不到任何吃貨/出貨/停損訊號
- 修復結果：重新同步 cloud-cache→cache 並用 production 路徑重算後，出貨訊號 **0 → 291 檔**恢復正常

這份報告回答的不是「怎麼修」（審計已寫），而是「**為什麼一個本來會動的東西，會三條一起壞掉而且沒人發現**」。

---

## 一、三個問題是三個獨立成因，但共用同一個結構弱點

| 問題 | 表面現象 | 真正成因 | 類別 |
|------|----------|----------|------|
| 吃貨永遠 0 | 訊號消失 | 移除 flow 機能時連帶砍掉，吃貨依賴 flow 卻沒被當成「下游依賴」盤點 | 移除機能未盤點依賴 |
| 停損全市場 0 | 欄位永遠空 | 停損語意是「持倉專屬」，卻被硬塞進「無進場價」的全市場掃描 | 訊號語意未分層 |
| 出貨顯示 0 實際 291 | 數字對不上 | 衍生快取（parquet 快照）在爛資料瞬間被寫出，且前端盲信、無驗證 | 衍生快取無完整性把關 |

共用的結構弱點：**系統把「會變的衍生結果」當成「可信的真相」儲存，而沒有任何一層在寫入/讀取時驗證它是否還對。** 這正是 `~/.claude` 架構紀律裡反覆強調的「多個 source of truth + invalidation 鏈斷掉」。

---

## 二、逐條根因分析

### 1. 吃貨：移除機能時沒有做「下游依賴盤點」

時間線（皆為本人 session，Claude 協作）：
- `cea3d932`（5/26）「移除全部投資部門別 (flow) 機能」——把 JPX 投資部門別/法人買賣超資料整包砍掉（很可能因為它只能做個股估算、準度不足）。
- 吃貨訊號定義 =「外資/法人連續買超 + 融資餘額下降」，**資料來源就是 flow**。flow 一砍，吃貨失去輸入，`accumulation_signal` 一起被移除。
- `bf333049`（5/27）清掉殘留引用。

**為什麼沒被發現**：移除 flow 時，關注點放在「把 flow 的程式碼/UI 清乾淨」，沒有反向問一句「**還有誰在吃 flow 的輸出？**」。吃貨就是那個下游消費者，它沒有自己的資料來源，是寄生在 flow 上的。砍掉上游＝默默砍掉下游功能，但 commit message 只記了「移除 flow」，沒記「吃貨功能一併下線」。

**教訓**：移除任何資料機能前，先 grep「誰讀這個資料/這個欄位」，把下游功能列成清單，明確決定每個下游是「一起下線」還是「換資料源續命」。

### 2. 停損：訊號語意（持倉專屬）沒有在資料模型上分層

- 停損數學上需要「進場價/主力成本」錨點。
- 全市場掃描的股票不是持倉、沒有進場價，程式在 `signal_service.py` 把 `start_price` **退化成「最新收盤價自己」**，於是停損門檻 = 最新價×0.95，最新價永遠不會跌破自己 → 結構性恆 0。
- 同一個 `analyze()` 同時服務「持倉視角」與「全市場視角」，但兩者語意不同：持倉有進場價、全市場沒有。程式用「拿最新價當 start_price」這個 hack 把兩者塞進同一條路徑，結果停損在全市場變成永遠不觸發的死欄位。

**為什麼沒被發現**：因為它「不報錯、只是永遠 0」。一個永遠 False 的旗標跟「市場上剛好沒人觸發」長得一模一樣，沒有測試或告警會抓到「這個欄位在全市場語意下根本不可能為 True」。

**教訓**：持倉專屬訊號（停損、時間停損、移動停損）不該出現在全市場欄位，或至少要在資料模型上標記「此視角不適用」，而不是用一個恆 False 的值魚目混珠。

### 3. 出貨：衍生快取在爛資料瞬間被凍結，且沒有完整性檢查

資料流：
```
cloud_fetch.py 寫 cloud-cache  ─(並發?)─┐
/cloud-sync: 複製 cloud→cache → run_signals_scan → 寫 signals_*.parquet
                                                        ↑ 前端全市場頁盲信這份
```

- 快照（parquet）是**衍生快取**：它是某個瞬間掃描的凍結結果，不是真相，真相是 `data/cache/*.csv`。
- 06-06 17:31 那份快照在一個「latest_price 讀得到、但 30 日窗算不出 exit」的爛資料瞬間被寫出（最可能：cloud_fetch 還在寫 cloud-cache 時、sync 同時 copy+scan，讀到半截/天數不足的價格檔）。
- 寫出後**沒有任何完整性檢查**：沒有人問「全市場 3747 檔、出貨/吃貨/停損全部 0，這合理嗎？」前端就直接信了，直到下次 sync。

**證據**：用 production 路徑對「同一份 cloud-cache 資料」重算，出貨穩定 ~290 檔；唯獨那份凍結快照是 0。即「快照與它自己的資料來源對不上」。

**為什麼沒被發現**：快照壞掉的方式是「全 0」，跟「市場平靜」無法區分；而且歷史快照的出貨數本來就忽高忽低（5/18~5/26 約 10、5/27 掉到 1），數字波動已經被視為正常，0 也就沒人警覺。

**教訓**：衍生快取寫入前要做 sanity check（例如「全市場三旗標同時全 0」應視為可疑、拒絕覆蓋上一版或標記 degraded）；資料抓取（寫 cloud-cache）與掃描（讀 cache）不可並發，要序列化成單一原子動作鏈。

---

## 三、共同根因：把「衍生結果」當「真相」存，且沒有 invalidation/驗證

- **兩個 source of truth**：`cloud-cache`（抓取寫入）與 `cache`（掃描讀取），中間靠一個「人要記得按」的 sync 複製步驟銜接。使用者「抓了最新」只更新 cloud-cache，analyzer 讀的 cache 沒同步 → 看到舊資料。
- **第三層衍生快取**：parquet 快照，又是對 cache 的凍結，再多一層 stale 風險。
- 三層之間**沒有 invalidation 鏈**：上游變了，下游不會自動失效或重算，全靠人工觸發，且觸發時機若撞上抓取就產生爛快照。

---

## 四、本次修復做了什麼

1. 同步 `cloud-cache/*.csv` → `data/cache/*.csv`（11238 檔，cloud 全數較新）。
2. 用 production 路徑 `run_signals_scan` 對全 3747 檔重算（504 秒、0 error）。
3. 覆寫 `signals_2026-06-06.parquet`：出貨 **0 → 291**、吃貨 0、停損 0（後兩者符合預期）。

## 五、尚未處理（需產品決策，本次未動）

- **吃貨復活**：需要先把 flow（或等價的法人買賣超）資料源弄回來，是產品決策。
- **停損分層**：把停損從全市場欄位移除、只在 watchlist/持倉頁顯示。
- **快照硬化**：寫入前 sanity check + 抓取/掃描序列化 + 三層快取收斂成單一 source of truth + invalidation 鏈。

## 六、流程層面要改的習慣（避免再犯）

1. 移除任何資料機能前，先 grep 下游消費者，列出「會跟著下線的功能」清單並寫進 commit message。
2. 任何「永遠 False / 永遠 0」的旗標都要被質疑：它是真的沒觸發，還是結構上不可能觸發？
3. 衍生快取（snapshot/parquet/json）一律附 sanity check，且不可在上游資料抓取進行中產生。
4. 看到快取寫的結論，先確認它對應哪一刻的資料（對照來源 mtime / 最後日期），不可盲信——這次正是靠「快照 latest_price 對應 cloud-cache、但旗標對不上」才抓到。
